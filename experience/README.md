# 带队经验

这间办公室里发生过的事，以及它们教会的规则。写给**下一个带这种队伍的人**——不是写给
插件的使用者（那是 [`../docs/design.md`](../docs/design.md) 的事），而是写给**坐在组长
位子上、要派活、要拍板、要收拾残局的那个人**。

每条都附**出处**：谁踩的、当时是什么症状、哪条读数抓出来的。没有出处的建议本书不收——
"我觉得应该这样"在管理上和在工程上一样不可靠。

**这几篇是中文写的**，与 `../docs/` 的英文体例不同：`docs/` 是插件的规格，读者是改代码的人；
这里是**带队经验**，读者是要坐进这个位子的人，写给中文使用者。这是有意的选择，不是遗留。

`leader` 这个角色**被雇进来时**，入职的那条私聊消息里带着本文件的绝对路径——也就是说，
坐进位子的人不用先知道有这些文档。**中途被 `office_configure` 提上来的组长不会收到那条消息**，
得由你（或办公室的记录）把路径告诉他。

## 篇目

- [`leading.md`](leading.md) —— 组长这个位子：决策权限怎么切、什么时候必须问用户、
  调度纪律、以及组长自己会怎么错。
- [`dispatch.md`](dispatch.md) —— 派活：工单该写什么、怎么算"完成"、怎么验收、
  怎么避免两个人做同一件事。
- [`evidence.md`](evidence.md) —— 读数是会骗人的：单点读数的陷阱、
  为什么"两栏相同"只是半个见证、怎么让一个结论可以被别人复核。
- [`people.md`](people.md) —— 用人：哪种任务配哪种人、顾问怎么用、
  怎么让组员顶回来、走人之前必须把什么留下。

## 一句话总结

**组长的工作不是想清楚所有事，而是把"谁在想什么、凭什么、到哪一步"变成别人能复核的东西。**
